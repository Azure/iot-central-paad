Legend — four kinds of line

Solid arrow — something really happens here. Either a step the phone performs on its own, or actual traffic the phone sends or receives.

The thirteen steps in words

Each card matches one numbered stop on the map. The “where to look” line names the real file or guide section, so a curious reader can open it next to the picture.

  1. 1 Somebody prepares, before the phone is involved

    Installing the app does not create anything in Azure. An administrator confirms that an existing setup is approved for this phone: an enabled individual enrollment, its supported provisioning endpoint, a hub the device may use, and — only if images are wanted — file-upload storage that already exists. They then deliver just the device's own inputs by a safe route.

    Nothing in this preparation is a licence to create resources, grant permissions or spend money; each of those would need its own approval.

    Where to look: guide section 6, administrator preparation.

  2. 2 Four values, and only four

    Three of them are ordinary names and one is a secret. The registration ID identifies the enrollment, the ID scope says which provisioning service to talk to, and the provisioning hostname is a public address. The device key is the secret — this one device's key, not a group key, not a service or owner key, and not an Azure password.

    The phone's capability model is filled in automatically and is public information, not a secret and not a serial number.

    Where to look: guide section 7, the field-by-field table.

  3. 3 The app checks before it connects

    Typed values and scanned codes go through the same decoder. Formats are checked, and the address must be one of the supported Azure endpoints. An arbitrary server or service-policy connection string is refused before any connection request. Redirects are also refused later by the network transport, rather than followed.

    Where to look: src/connection/credentials.ts.

  4. 4 The phone signs its own temporary pass

    Using the device key, the app builds an expiring shared-access signature. Azure can verify that signature without the app ever sending the raw key as the request body, and TLS protects the journey. This authenticates a device, not an Azure administrator.

    These passes currently last one hour, so the phone's clock matters. Use Reconnect to connect with fresh authorization; the app does not silently renew or retry forever.

    Where to look: src/connection/dps.ts (the expiry is one hour from now) and guide section 8.

  5. 5 Registration is an ordinary web request

    This surprises people: the first contact is not messaging. It is an HTTPS PUT to the provisioning service, carrying the registration ID and the phone's public model identifier. The service checks the signed pass against the enrollment.

    Where to look: src/connection/dps.ts builds /<id-scope>/registrations/<registration-id>/register with provisioning API version 2019-03-31.

  6. 6 Waiting politely for the answer

    Assignment is not instant. While the service says “still assigning”, the app asks again with HTTPS GET, honouring the wait the service requests and its own overall deadline. This is a bounded wait, not an endless retry loop.

    The answer names the assigned hub and the assigned device ID. That device ID can be different from the registration ID you typed, and the app keeps both. A saved registration ID is not a promise of tomorrow's assignment: on reconnect the phone can be assigned again.

    Where to look: src/connection/dps.ts — the polling loop honours the service's retry guidance and checks the returned hostname before trusting it.

  7. 7 One direct connection to the assigned hub

    Now messaging begins, and it goes straight to the hub — provisioning is not in the middle of it. The app signs a second pass, this time for the assigned hub and device, and opens MQTT over secure WebSockets on the ordinary secure-web port, 443. The hub username carries the public model identifier and the device API version. Redirects are refused and the system's certificate and hostname checks stay switched on.

    Where to look: src/connection/legacyHub.ts and modules/paad-device, the repository's restricted secure-socket native module.

  8. 8 Saved first, adopted second

    The order matters. Only after the connection succeeds are the credentials written into the phone's secure storage, and only then does the app start using the newly connected client. A failed write is reported as an error rather than quietly ignored.

    Disconnect ends the session but keeps the saved credentials. Reconnect uses them again with a fresh pass. Forget credentials is a separate, confirmed action that removes the local copy and any imported Azure context from this phone. It does not delete an enrollment, a hub device, a registry record or anything already uploaded, and it is not key revocation.

    Where to look: src/contexts/storage.tsx and src/hooks/iotc.ts.

  9. 9 What the phone sends out

    On that same connection the app asks for the device twin, reports the properties it knows, sends telemetry from whichever sensors are enabled and available, and submits acknowledgements and command replies.

    All of these are published at QoS 0, which in plain English means the app does not wait for the broker to say “received”. So “submitted” in the app means the phone handed it over locally — it is not evidence that Azure stored it.

    Where to look: guide section 10.

  10. 10 What comes back in

    The same connection carries the twin's first values, later desired-property changes, and commands such as a torch pulse or a request to change a sensor interval.

    Three things that look alike are deliberately kept apart: receiving a command, carrying it out, and submitting a reply. Missing torch hardware or permission can produce an error reply. A sensor-enable or interval request can be accepted without proving a fresh reading. A reply the phone sends is still only a submission.

    Where to look: guide section 9, the tool-by-tool table.

  11. 11 A picture takes a different road

    Image bytes are never an MQTT message. The app limits the content to 20 MiB, then does three HTTPS steps: ask the hub for a place to put the file, PUT the bytes straight into Azure Blob Storage using the limited permission the hub handed out, and finally tell the hub how it went. Both the upload and the notification must succeed.

    The result is an HTTP outcome, not a messaging acknowledgement, and it says nothing about what happens to the file afterwards. These bytes do not pass through a registry namespace.

    Where to look: src/connection/upload.ts.

  12. 12 The optional namespace, above it all

    Some organisations put a device registry namespace above provisioning and the hub. It holds service links, eligible-hub configuration and device inventory. All of that is cloud-side configuration, done by an administrator.

    The phone's side of the story does not change at all: the same four inputs, the same registration, the same hub connection. No namespace name, subscription or operator sign-in is needed in the connection form, and there is no third connection from the phone. An optional imported snapshot can display namespace and subscription context later; that is not a live registry lookup.

    Where to look: operator guide and guide section 5.

  13. 13 Someone else checks, with their own access

    The phone can only report what it did. Independent evidence comes from an authorised operator who reads Azure separately. First the phone submits a fresh marker — a new value agreed for this attempt, never a reused one from an old run. Then the operator reads: the assignment held by provisioning; the hub's own device record, checking the identity, the public model and that exact marker; and, only where a namespace is used, the inventory record whose external device ID matches the actual assigned ID.

    Seeing the marker in the hub's record proves that this reported value reached that cloud record. It does not prove a downstream system consumed the telemetry, that the phone is still online, or that any physical sensor works. Proving that a new inventory record was created automatically needs authorised before-and-after evidence; finding an already-matching record proves no new creation.

    Where to look: guide section 10, “A guided independent proof” and the existing scripts/ci/verify-mobile-proof.js, which performs bounded read-only checks using an operator's own authorised session.

Three ways an organisation can be set up

The big map shows the phone path shared by both DPS scenarios; its optional namespace applies only to B. These separate insets show which services are used in each setup. Direct Hub, C, bypasses DPS.

  • A. Classic provisioning and hub

    The phone registers, is told which hub to use, and connects there. The optional namespace box in the big map is not used in this case.

  • B. A registry namespace above them

    The phone uses the same connection inputs and protocols. Namespace inventory is cloud-side; an operator can confirm it separately or provide a historical context snapshot.

  • C. Straight to a hub

    Steps 4 to 6 are skipped: the hub, device ID and key all come from a connection string. Everything after step 7 works the same way. This route on its own establishes no namespace inventory result.

What counts as evidence, and what does not

The phone's own words

  • Submitted means the app handed the message to its connection locally. Outbound messages use QoS 0, so no acknowledgement is waited for.
  • An upload's acknowledged outcome is a completed HTTP operation, not a messaging acknowledgement, and not proof of downstream processing.
  • Activity keeps a deliberately small, in-memory record — up to 120 rows and 64 KiB including the latest facts, with repeated failures grouped. Payloads, coordinates, image bytes, keys and proof markers are not kept. Diagnostics logs are a separate list.
  • The absence of an error is not evidence of delivery.

Independent evidence

  • Comes from an authorised person reading Azure with their own access, not from the phone.
  • Needs a fresh marker for each attempt. A marker reused from an earlier run proves nothing about today.
  • A matching inventory record that already existed does not prove automatic creation. That claim needs authorised before-and-after evidence.
  • Even with an operator's imported snapshot, the app still shows registry status as Not checked, because it never performed a live lookup.

The optional snapshot: helpful, but historical

You can use PAAD without importing anything. The app never signs in to Microsoft Entra and never calls registry, management or operator APIs with the device key. Separately, an operator can export approved resource information and hand it over as text.

If that text is imported, the app checks its shape and that it belongs to the same assigned device and hub, then shows it as operator-provided context. It is a historical snapshot, not a live lookup and not an authenticated assertion. Removing the snapshot removes only the local copy. Never paste a key, a connection string or an access token into that field.

When something goes wrong

A short beginner's version. The guide's troubleshooting table is the fuller one.
What you see What it usually means
Credentials rejected A field is in the wrong role or has stray whitespace, or the enrollment does not match. Check with the administrator; never ask for a broader key.
Authentication refused The enrollment, key or scope do not line up — or the phone's clock is wrong, which breaks a time-limited pass.
Provisioning did not complete Step 6 ended without an assignment. An operator needs to inspect allocation and, in the namespace case, service links and permissions. The phone cannot repair cloud configuration.
Endpoint not approved The address is not a supported Azure endpoint. The answer is the correct hostname, never disabling a security check.
Connection interrupted An established session dropped: network loss, suspension, or an expired pass. Reconnect. It is not a diagnosis of a wrong key.
A sensor has no reading, or the torch does nothing Check hardware, permissions and the reported command outcome. A healthy cloud connection does not guarantee a working sensor; a rejected torch request can still produce an error reply.
Secure transport required The app is not running as a correctly rebuilt native build with this repository's secure transport.
Offline simulation label is shown There is no live cloud connection at all, so nothing on screen is cloud evidence. This is different from running on an emulator or a simulator, which can make real connections.

What this picture deliberately does not claim

  • No resource is created. Installing or connecting the app never creates an Azure service, an enrollment, a storage account or a permission.
  • No Azure operator login is needed. Device authentication is separate from an operator account. Subscription and namespace information may appear in an imported context snapshot, but no operator credential or phone-to-registry connection is used.
  • A simulator build is not a signed phone app. An artifact produced for a desktop simulator is a different thing from a signed build installed on real hardware, and a successful build is not a cloud test.
  • This diagram is not live evidence. As of 2026-09-20, the redesigned experience has retained-DPS Android emulator and iOS Simulator acceptance, plus an in-place Windows emulator update. Exact sources, cloud proof, restoration and remaining limits are recorded in the beginner guide and acceptance ledger. Physical-phone acceptance remains separate; this page changes no code, creates no build and verifies nothing.
  • Device and environment examples are invented. Public service hostnames and the phone model identifier are real reference values. No live lab identity, private resource path, key or proof marker appears on this page.
